# StackChan 自建链路 vs 云链路 对比 (2026-08-05)

## 一、自建链路 (stackchan.selfhost) 实现了什么

**核心链路**: M5Stack CoreS3 机器人 → Tailscale Funnel(公网 443) → 本机
xiaozhi-esp32-server (docker) → 融合网关 → 本机 4 个 AI agent。

| 能力 | 状态 | 说明 |
|---|---|---|
| 语音对话 | ✅ | ASR=阿里百炼 paraformer-realtime-v2 流式 / LLM=deepseek-v4-flash(关思考) / TTS=EdgeTTS 粤语 |
| **真·主动播报** | ✅ | agent 任务完成 → 网关 `/api/push` → 设备**立即打断播报**(不等唤醒), 云链路做不到 |
| 语音指挥 agent | ✅ | 「让 codex 查一下…」→ agent_query → 在 agent 自己窗口执行 |
| 结果回流播报 | ✅ | agent 完成后 hooks 回流 → 机器人念摘要(50 字内) |
| 待确认回环 | ✅ | claude 的权限确认 → 机器人念问题 → 语音回答 allow/deny 回写 |
| 唤醒 | ✅ | 双击(首要) / 阿松 / 摸头; 播报中双击=打断并聆听 |
| 设备控制 | ✅ | 点头/摇头/转向/表情/拍照/灯环 |
| 数据可控 | ✅ | 配置/日志/密钥全在本机, 不依赖第三方智能体云 |
| 局域网隔离穿透 | ✅ | AP 设备隔离也能用(Tailscale Funnel 公网中继) |

## 二、自建链路还没实现 / 已知不足

| 不足 | 现状 | 影响 |
|---|---|---|
| Funnel 网络抖动 | 连接偶发死亡/握手失败(几秒~20秒) | 唤醒偶发「连接中」、推送偶发延迟; 属公网中继, 换更稳链路可缓解 |
| 依赖本机在线 | 电脑关机/断网机器人不可用 | 云链路无此限制 |
| 设备端 AEC 不可用 | 会导致音频死循环, 播报时靠关麦克风缓解 | 播报中听不清用户插话(双击打断) |
| 识别率 | 受阿里百炼 ASR 服务质量影响(今日曾 27s 延迟, 已修复) | 偶发误识别/慢 |
| 触摸 I2C 抖动 | 双击偶发被误判成手势 | 偶发唤醒异常 |
| 灯环物理显示 | 状态色偶发与预期不一致 | 视觉反馈偶发不准 |
| 多轮上下文 | 单会话内存有限(nomem) | 长时间对话记忆弱 |

## 三、与云链路 (xiaozhi.me) 对比

| 维度 | 自建链路 | 云链路 (xiaozhi.me) |
|---|---|---|
| 服务器 | 本机 docker + Tailscale Funnel | 第三方云 |
| 主动推送 | ✅ 立即打断式 | ❌ 无推送 API, 只能排队等唤醒念 |
| 唤醒播报 | 唤醒即聆听(不自动播) | 唤醒优先读队列 |
| 语音/LLM 模型 | 自己配(阿里/DeepSeek/Edge) | 平台预设 |
| agent 接入 | 本机 hooks 直连 4 个 agent | 需 MCP 桥接 |
| 成本 | 免费音色 + API 按量 | 平台计费/额度 |
| 稳定性 | 依赖本机 + Funnel 公网 | 依赖第三方云 SLA |
| 隐私 | 对话记录在本机 | 对话在第三方云 |
| 部署门槛 | 需要 docker/tailscale/会刷固件 | 开箱即用 |

**结论**: 自建链路的**决定性优势是「真·主动播报 + 本地可控 + agent 深度集成」**;
代价是部署门槛和网络依赖。云链路适合快速体验, 自建链路适合深度使用。

## 四、当前验收状态

- 唤醒(双击/阿松/摸头) → 聆听 → 语音 → ASR(3~5s) → LLM → 播报: **基本打通**
- 主动播报: **打通**(队列去重 + 推送成功移除)
- 音量/灯/表情等设备控制: **打通**
- 已知待办: Funnel 稳定性、识别率调优、AEC 替代方案、灯环显示一致性
